# 设备内存可见性 · 两套方案（2026-11-14）

> 文档生命周期：**HISTORICAL**（历史方案与阶段性实施记录）。本文记录 2026-11-14 的方案、评审与当时验证边界；其中“已实施”“未烧录/未推送”等均为当时快照，不代表当前 HEAD、设备镜像或当前验收状态。当前实现须以源码和最新验收证据核对。

**背景**：旧 web 设备面板有「空闲堆」（`web/config-api.js:99` `free_heap`，i18n「空闲堆」），随 web 整体删除后界面上消失。数据其实没丢——`device.status.heap` 有 `free / min_free / largest / internal_largest`，比旧 web 还全；丢的是展示入口：小程序首页「设备信息」只读 `device.info`，而契约规定 `device.info` 是身份查询、不含运行态。

两个方案相互独立，可分别评审、分别实施。

---

## 方案 A · 恢复「空闲堆」（纯客户端，不改固件）

### 范围
`pages/index/index.js`，约 25 行；不动固件、不动契约。

### 改动点
1. `buildInfoRows(device, status)`（index.js:826）增加可选第二参；`status` 存在时追加三行：

   | 行 | 来源 |
   |---|---|
   | 空闲堆 | `heap.free` |
   | 历史最低 | `heap.min_free` |
   | 最大可用块 | `heap.largest` |

2. 登录成功后（index.js:747 附近）在 `deviceInfo()` 之后补一次 `protocol.deviceStatus()`，与身份行一起 `setData`。
3. `onShow` 已连接且已登录、`deviceInfo` 为空时（index.js:238）同样补拉一次。
4. 未登录时不发请求，只显示一行占位：`内存：登录后可见`。
5. 新增小工具 `kb(n)` → `29.9KB`（本仓无现成 `formatBytes`）。

### 失败处理
`deviceStatus()` 失败只写日志、不阻塞面板，三行显示 `—`；旧固件缺该命令时同样静默降级。

### 成本
一次 `device.status` 响应约 1.2–1.5KB / ~75 帧 / ~2s（仅登录后一次，不在 `onShow` 反复拉）。

### 测试
- 登录 → 三行出现，数值与串口 `diag: heap free=…` 的差值 < 2KB（采样时刻不同，不要求相等）；
- `min_free` 应 ≤ `free`；
- 断开重连后只在新登录时刷新，不重复拉；
- 未登录时不出现请求（日志无 `device.status`）；
- **迟应丢弃回归（必测）**：拉取过程中断开或切换设备，迟到的 `device.status` 应答不得落到新设备界面上（`ble.deviceId` 变化即丢弃，界面保持清空/新设备值）。

### 风险
`device.status` 需要 token（`ble_cmd.c:534`，仅 `auth.login`/`device.info` 免 token），所以只能登录后显示——这是接口本身的约束，不是方案缺陷。

## 方案 B · 暴露任务栈水位（固件 + 契约 + 小程序）

> **状态：已实施（2026-11-14）**
> 固件 `49707a9`（`diag.c/h`、`cmd.c`、`tests/diag_watch_names.py`）；客户端 `ee61788`（契约 + 内存行）。
> 构建：`idf.py build` 0 error / 0 warning，镜像 1,174,656 B；host 用例 25 条名字、0 超长。
> 未烧录、未推送。

### B1 固件（`main/diag.c`、`main/diag.h`、`main/cmd.c`）

1. **抽取可复用函数**（不改日志口径）：
   ```c
   /* 返回 false = 表内任务一个都没找到 */
   bool app_diag_stack_snapshot(size_t *min_bytes, const char **min_task,
                                char *low, size_t low_len);
   ```
   - 逻辑取自现有 `app_diag_dump_stack_water()`（diag.c:234），遍历同一张 `s_stack_watch`；
   - `app_diag_dump_stack_water()` 改为调用它并打印，保持 `diag: stack water: min=… low:…` 输出不变；
   - **调用方自带缓冲**，不复用 `s_stack_line`，避免 diag 任务与命令任务共享 static。
2. **`device.status` 增字段**（cmd.c:1323 之后）：
   ```c
   stack = cJSON_AddObjectToObject(root, "stack");
   if (stack) {
       size_t min_bytes = 0; const char *min_task = "?"; char low[160] = "";
       if (app_diag_stack_snapshot(&min_bytes, &min_task, low, sizeof low)) {
           cJSON_AddNumberToObject(stack, "min_free", (double)min_bytes);
           cJSON_AddStringToObject(stack, "min_task", min_task);
           if (low[0]) cJSON_AddStringToObject(stack, "low", low);
       }
   }
   ```

### B2 契约（`contract/v1/commands.json`）

`device.status.data` 增加：
```json
"stack": { "min_free": "number", "min_task": "string", "low": "string（<2KB 的任务列表，可空）" }
```
`notes` 补一句：历史最低、重启清零、仅覆盖表内任务。

### B3 小程序

在方案 A 的三行之后追加：
- 任务栈最低（`stack.min_free`，单位 B/KB）
- 对应任务（`stack.min_task`）
- 低于 2KB 的任务（`stack.low`，过长按前 3 项截断）

旧固件无 `stack` 时这两/三行自动隐藏。

### 约束（实现时必须遵守）

| 约束 | 说明 |
|---|---|
| 任务名 < 16 字符 | `xTaskGetHandle` 超长会 assert（1.3-44 踩过）；表里已用 FreeRTOS 截断名 |
| 历史最低，不是当前值 | `uxTaskGetStackHighWaterMark` 自任务创建起单调不增，重启清零 |
| 只覆盖 `s_stack_watch` 的 24 个任务 | 新任务需加表；`uxTaskGetSystemState` 能看全部但要 ~1.3KB RAM，已否决 |
| 无新 DRAM | 名字表在 flash；`low` 由调用方栈上缓冲 |
| 体积 | 响应 +约 120B（`low` 为空时约 +60B） |

### B4 测试

固件侧：
- 上电后调 `device.status`，`stack.min_free` 应与同刻 `diag` 日志的 `min=…` 相等，或更小（两次采样之间水位只降不升）；
- 表内任务不存在时跳过、不崩；
- `low` 为空时字段省略，JSON 仍合法；
- 连续调用 10 次无内存增长（无泄漏）。

小程序侧：
- 登录后 5 行齐全；`low` 过长时截断显示且不撑破卡片；
- 用旧固件（无 `stack`）验证自动隐藏；
- 回归 #21：它已调用 `device.status`，新增字段不影响解析。

## 共同边界

- 两个方案都是**加法字段**，不 bump 协议版本（仍 `protocol_versions: ["1.0"]`），旧客户端忽略新字段；
- **不并入** WIFI-OP-RESOURCE-RACE 补丁，各自单独 commit / 单独申请；
- 方案 A 可先上真机验证，不依赖固件；
- 方案 B 的固件部分需要单独的烧录窗口（当前烧录仍未授权）。

## 评审点

1. 方案 A 是否足够（只恢复「空闲堆」，含历史最低/最大块）；
2. 方案 B 的 `stack` 放 `device.status` 是否同意（不塞 `device.info`）；
3. `low` 字段要不要（多 ~60–100B；只留 `min_free` + `min_task` 也够用）；
4. 是否需要在 T4 验收报告里同步显示内存（那是第三处改动，本次未含）。

## 评审意见落实（v2，2026-11-14）

### A · 已按意见实施

| 意见 | 落实 |
|---|---|
| 「历史最低」与 B 的栈最低混淆 | 行文案改为 **堆空闲 / 堆历史最低 / 堆最大可用块**，三项都带「堆」字前缀 |
| 未登录占位改折叠块、避免跳动 | `pages/index/index.wxml` 增 `.mem-block`（`min-height:150rpx`），未登录显示「堆内存：登录后显示」，登录后原地换成三行，不改变外框高度 |
| `<1KB` 显示 B 而非 `0.0KB` | `formatBytes()` 按 1024 换算；`<1024` 输出 `nB`，否则 `x.xKB` |

实现位置：`pages/index/index.js`（`formatBytes`、`buildMemRows`、`_refreshMemory`、登录成功/连接成功/回前台三处触发、断开清空）、`pages/index/index.wxml`（内存块）、`app.wxss`（`.mem-block`）。已过 `node --check`，**未上真机**。

### B · 修订

1. **契约语义钉死**：`stack.min_free` = 「`s_stack_watch` 内所有任务中，历史最低剩余栈的最小值」；`min_task` 为该任务名。与 heap 侧 `min_free`（ESP-IDF 堆历史最低）语义平行，命名保持一致。
2. **`low` 保留**，维持「空则省略」；理由：诊断价值 > 60–100B 体积。
3. **单位注释**：抽函数时写明 `uxTaskGetStackHighWaterMark()` 返回 StackType_t 字数，输出前 `× sizeof(StackType_t)`（现实现已是此口径，注释防止后人按字解析）。
4. **B4 测试第 1 条补采样顺序**：`device.status` 采样在 diag 之后时水位应为「相等或更小」；若顺序反过来（diag 在后）则「相等或更大」也合法。判据必须写明顺序依赖，否则换顺序会误判。

### 句柄表 → 启动校验（已定稿）

原建议「表内直接存 `TaskHandle_t`」经评审**不采纳**：

- 句柄有生命周期，`wifi_restart`、`ble_cmd` 等任务并非全部常驻；缓存后任务被删即悬空访问，属未定义行为，比 assert 更隐蔽；
- 要安全用句柄需为 24 个任务逐个加注册/注销钩子，侵入面与本功能不成比例；
- 现有 `strlen(name) >= 16` 跳过已构成运行期护栏。

**改为「启动校验 + host 字符串长度用例」**：

1. `app_diag_start()` **开头**（创建 diag 任务之前）校验 `s_stack_watch` 全部名字 `< 16`；
2. 任一超长 → `ESP_LOGE` 并**直接不启动监控任务**（宁可整个关掉，不带着已知坏表跑半监控，避免误导诊断）；
3. host 侧加一条用例遍历名字长度（`tests/` 下，与 `syntax_check.py` 同风格），把问题挡在提交前。
